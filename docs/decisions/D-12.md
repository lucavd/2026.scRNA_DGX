# Decisione

1. **Processi freddi.** Ogni ripetizione è un processo nuovo con le cache JIT vuote: `NUMBA_CACHE_DIR` (e `CUPY_CACHE_DIR` per la GPU) puntano a una cartella nuova a ogni ripetizione, su entrambe le macchine. Ogni ripetizione corrisponde quindi alla ripetizione 1 di marzo, che è il termine di confronto con marzo.
2. **Gruppi.** I gruppi di co-occorrenza, arricchimento di vicinato e ligando-recettore sono il Leiden della ripetizione 1 CPU sul DGX. Quella ripetizione usa il proprio Leiden; tutte le altre (DGX 2-5, GPU 1-5, controllo CPU 1-5) leggono il file con `--labels-from`. Leiden si esegue e si cronometra sempre.
3. **CPU del DGX.** Allocazione esclusiva del nodo `poddgx02`; ogni ripetizione è un passo `srun --cpus-per-task=100 --cpu-bind=cores`. Con `CR_CORE` e 2 thread per core sono 50 core fisici con i loro 100 thread, la stessa richiesta del riferimento CPU dello scRNA. I dati si copiano in `/dev/shm` del nodo con controllo md5 (il nodo non ha disco locale, `/home` è NFS). Immagine: la stessa del server, `lucavd/sc-benchmark-spatial:latest` (id `sha256:738c8cc7301590c95a3ddc3b7dd74bafeefee1f1ce188063e14a166a707a6ddd`), convertita in SIF.
4. **Ramo separato.** Codice e risultati stanno sul ramo `rerun-spatial-v2`, in un worktree a parte (`/mnt/wwn-0x5000039d58caca35/2026.scRNA_DGX_S1`), così le chat degli step successivi lavorano su `main` senza interferenze. I dati si montano in sola lettura dal checkout principale.
5. **File grandi.** I file `*_clusters.csv` (circa 10 MB l'uno) non entrano in git, tranne i tre file di etichette usati come gruppi; l'md5 di ogni file di `SPATIAL/results_v2/` sta in un manifest tracciato.
6. **Confronto CPU-GPU.** `compare_spatial_results.py` riceve `--cpu-results-dir` e `--output-dir`, per confrontare file prodotti su due macchine. Il calcolo della concordanza non cambia.
7. **GPU nel container solo per i run GPU.** Lo script CPU non usa la GPU; `--gpus all` si passa solo ai run GPU.

# Motivazione

Il brief chiede un processo per ripetizione e gli stessi gruppi per CPU e GPU, senza altri cambiamenti. Con Singularity sul DGX la cache numba finirebbe nella home condivisa e verrebbe riusata fra ripetizioni, mentre con docker sul server si perde a ogni run: senza il punto 1 le due macchine misurerebbero cose diverse. Il punto 3 rende il riferimento CPU dello spatial uguale per risorse a quello dello scRNA, come chiede [CPU dello spatial: DGX come riferimento, server come controllo (D-11)](D-11.md).
